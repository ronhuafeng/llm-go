# Review

## 目标

在用户固定的范围内识别缺少当前保留证据的 legacy 候选，只报告有证据支持的
findings，不修改文件。

## 输入门槛

- 范围必须能表示为明确的 capability、目录、模块、文件或提交差异；否则先询问。
- review 是只读分支。修改请求但没有已确认 findings 时仍先完成本 review。

## 流程

1. 复述固定范围并检查当前工作树，区分范围内现状和既有用户修改。
2. 在范围内寻找用户点名的候选，以及旧类型、旧 schema、adapter、deprecated
   API、兼容路径、fallback、双执行路径、未调用代码及失效测试、自动化或文档。
3. 为每个候选画出完整 closure，检查定义、直接与间接消费者、构建和配置入口、
   公开与人类政策契约、上游事实、运维状态及相关运行证据。文本搜索只用于发现
   候选，不能代替调用关系或 owner 判断。
4. 将候选判定为：
   - `finding`：证据证明它已被替代、不可达、重复或与当前契约冲突；
   - `required`：至少一项共享政策中的保留证据明确要求它；
   - `undetermined`：存在具体证据缺口，尚不足以安全删除。
5. 运行与风险相称的只读检查、测试、构建、生成验证、runtime observation 或
   external-state inspection。每个候选都必须得到一种判定。

## 报告

先按影响程度列出 findings。每项包含：

- 本次 review 内唯一的 ID，例如 `LP-01`；
- 准确位置和完整 closure；
- 支持保留与支持删除的当前证据；
- 定义到消费者、owner 和外部契约的关系；
- 当前行为、影响和判定；
- 应删除的完整闭包与必须保留的独立切片；
- 删除安全风险、证据缺口及预期验证；
- 不扩大固定范围的最小修改。

随后列出确认 `required` 的候选、`undetermined` 的具体证据缺口，以及执行过的验证。
没有 findings 时明确说明，并报告仍存在的证据盲区。

完成报告后停止，不实施修复。
