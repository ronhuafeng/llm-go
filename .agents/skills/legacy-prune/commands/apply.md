# Apply

## 目标

在固定范围内完整关闭当前对话已经确认的 findings，删除无支持闭包并保留具有独立
证据的切片。

## 输入门槛

- findings ID 和 review 时的用户范围必须明确；缺失时返回 review，不直接修改。
- apply 只关闭这些 findings，不重新发起全仓审查或顺带清理。

## 流程

1. 检查当前工作树并复述固定 scope 与 findings ID。重新确认每项 finding 的保留和
   删除证据仍成立；实施状态以当前工作树和 diff 为准，不创建独立进度账本。
2. 删除无支持的完整 closure 并更新消费者；保留具有独立证据的最小切片。若删除
   abstraction 会移动复杂度、复制 owner 或丢失事实，改为深化现有实现并报告原因。
3. 同步更新受影响的测试、fixture、automation、generated material、configuration
   和当前文档，使它们只描述修改后的现实。
4. 检索旧名称、旧输入形状、旧 schema、adapter、fallback、并行实现、死代码和
   冲突表述。逐项核对残留的独立保留证据，不凭名称继续删除。
5. 按软件仓库 profile 选择与风险相称的验证；条件允许时补充只读 live validation
   或 external-state inspection。
6. 检查完整 diff，按 ID 确认 finding 已关闭、unsupported closure 无残留、独立切片
   仍正确、没有引入替代兼容路径，且无关用户修改未被纳入。

如果 finding 已失效、出现新的保留证据、关键契约无法确定，或修复必须扩大授权范围，
停止受影响的删除并报告缺失证据；其他 finding 可以独立继续，不留下半套实现。

只有在失败可重复，并且有证据排除本次 diff 对测试、被测代码、配置、构建入口和依赖
路径的影响时，才能报告验证失败与本次修改无关。优先使用不包含本次修改时同样失败的
基线证据；证据不足时标记为 `unresolved`，不得称为既有问题。

## 完成条件

- 每项已确认 finding 均已修复，或因新证据明确说明无法安全实施；
- 被删除能力的完整 owned closure 没有失效残留；
- 每个保留切片都有共享政策认可的当前证据；
- 适用验证通过，或失败已证明与本次修改无关；
- 剩余设计、owner 和外部契约内部一致；
- 没有纳入无关用户工作，也没有越过授权的完成层级。

最终按 ID 简要报告每项 finding 的关闭结果、删除与保留证据、验证结果和明确限制。
